# User Spec: Миграция FanFanTulpan с Telegram на MAX Mini App

## Что делаем

Полная миграция приложения FanFanTulpan с платформы Telegram Mini App на платформу MAX Mini App. Миграция охватывает два уровня:

**Фронтенд:** замена Telegram WebApp SDK (`window.Telegram.WebApp`) на MAX Bridge API (`window.WebApp`). Переписываются типы, хук инициализации, хранилище корзины (CloudStorage → сервер), обработка диалогов (нативные `alert`/`confirm`).

**Бэкенд:** замена aiogram на httpx + прямые HTTP-запросы к MAX Bot API (`platform-api.max.ru`). Переписывается валидация `initData` (собственная HMAC-SHA256 без aiogram), бот-клиент с long polling, отправка уведомлений менеджеру.

Бизнес-логика, вёрстка, навигация **не меняются**. База данных расширяется таблицей для хранения корзины пользователя на сервере.

---

## Зачем

Клиенты цветочного магазина используют мессенджер MAX. Без этой миграции они не смогут открыть приложение: MAX не поддерживает Telegram WebApp SDK, бот не запустится, заказы не будут поступать. Миграция открывает новую аудиторию пользователей MAX при сохранении всего текущего функционала.

---

## Контекст и ограничения

- MAX-бот уже создан в панели разработчика (`dev.max.ru`)
- Алгоритм валидации MAX initData идентичен Telegram (HMAC-SHA256, ключ `"WebAppData"`) — подтверждено документацией `dev.max.ru/docs/webapps/validation`
- Корзина хранится на сервере (БД) — единственное хранилище; DeviceStorage и localStorage не используются
- Бэкенд не использует Python SDK для MAX (его нет) — только httpx к REST API
- Тестирование в реальном MAX Mini App — отдельный этап после деплоя
- Три TBD уточняются при тестировании (см. конец документа)

## Пользовательские флоу

### Флоу 1: Открытие приложения в MAX
1. Пользователь нажимает кнопку "Открыть магазин" в чате с ботом
2. MAX открывает Mini App, загружает MAX WebApp SDK
3. Приложение инициализируется (без вызова `expand()` — в MAX нет аналога)
4. `initData` отправляется с каждым API-запросом в заголовке `Authorization: tma <initData>`
5. Бэкенд валидирует подпись через HMAC-SHA256, пользователь видит каталог

**Edge cases:**
- MAX SDK не загрузился (`window.WebApp` недоступен) → приложение показывает ошибку / деградирует gracefully (уже обрабатывается в хуке инициализации)
- `initData` невалидна → бэкенд возвращает 401 → пользователь видит сообщение об ошибке

### Флоу 2: Сохранение корзины (серверное)
1. Пользователь добавляет или убирает товар в корзине
2. Фронтенд синхронизирует изменение с сервером через API (добавление / обновление количества / удаление позиции)
3. При открытии приложения корзина загружается с сервера — состояние сохраняется между устройствами и сессиями
4. После успешного оформления заказа корзина на сервере очищается

**Edge cases:**
- Сервер недоступен при добавлении товара → показывается сообщение об ошибке, локальное состояние корзины не теряется до следующей синхронизации
- Пользователь открыл приложение на двух устройствах одновременно → на каждом устройстве загружается актуальное состояние с сервера при открытии

### Флоу 3: Оформление заказа — получение телефона
1. Пользователь нажимает "Заказать" в корзине
2. Если `userInfo.phone` пустой — показывается `window.confirm()` с подтверждением
3. Вызывается `WebApp.requestContact()` согласно документации MAX
4. Фронтенд получает телефон из ответа и вызывает `PUT /users/me/phone`
5. Оформление заказа продолжается автоматически

**Изменение vs Telegram:** polling `fetchUserInfo` (15 попыток × 1 сек) убирается. Бот-механизм не работает в MAX (бот не получает contact-сообщения), используется прямой REST вызов.

**Edge cases:**
- Пользователь отклонил запрос контакта → показывается `window.alert()` с объяснением, заказ не оформляется
- `PUT /users/me/phone` вернул ошибку → показывается сообщение об ошибке, пользователь может повторить

### Флоу 4: Приветственное сообщение от бота
1. Пользователь впервые открывает чат с ботом (`bot_started` event)
2. Бот загружает фото `api/images/fanfan-main.jpg` через `POST /uploads` → получает media token
3. Отправляет сообщение с фото + текстом + inline-кнопкой "🌸 Открыть магазин" (`open_app`)
4. Нажатие кнопки открывает Mini App

**Edge cases:**
- Загрузка фото не удалась → бот отправляет сообщение только с текстом и кнопкой (без фото)

### Флоу 5: Переключение режима (только для администратора)
1. Администратор отправляет `/mode` боту
2. Бот отвечает inline-клавиатурой: "Режим администратора" / "Режим клиента"
3. При нажатии кнопки — mode обновляется в БД, бот подтверждает

**Edge cases:**
- Пользователь не является администратором → бот отвечает "Команда доступна только администраторам"
- Callback обрабатывается только от корректных payload'ов (`mode_admin`, `mode_user`)

### Флоу 6: Уведомление менеджера о заказе
1. Заказ создан через REST API
2. Бэкенд отправляет сообщение менеджеру через MAX Bot API
3. Форматирование: Markdown (`**жирный**`) вместо HTML (`<b>`)

**Edge cases:**
- MAX Bot API вернул ошибку → уведомление не доставлено, заказ при этом уже создан (поведение аналогично текущему Telegram-поведению)

## Что меняется в коде (обзор)

**Фронтенд (app/):**
- `index.html` — скрипт SDK
- `types/telegram.d.ts` → `types/max-webapp.d.ts` — типы WebApp API
- `hooks/useTelegramWebApp.ts` → `hooks/useMaxWebApp.ts` — инициализация SDK
- `hooks/useCartPersistence.ts` — CloudStorage → серверное API (новые эндпоинты `GET/PUT/DELETE /api/cart`)
- `App.tsx` — диалоги, ссылки, импорты
- `components/Cart.tsx` — requestContact flow, убрать sendData и polling
- `components/AdminProductCard.tsx` — прямое обращение к `window.Telegram` → `window.WebApp`

**Бэкенд (api/):**
- `auth.py` — замена aiogram-валидации на HMAC-SHA256
- `main.py` — полная перезапись: MaxBotClient + long polling + обработчики
- `notifications.py` — httpx вместо aiogram.Bot, HTML → Markdown
- `requirements.txt` — убрать aiogram
- `routers/cart.py` — новый роутер: `GET /api/cart`, `PUT /api/cart`, `DELETE /api/cart`
- `database.py` — новая таблица `user_cart` (user_id, good_id, count)

Автоматических тестов в проекте нет, проверка ручная. Для L-фичи достаточно:

## Как проверить

### Агент (автоматически)
- `cd app && npm run build && npm run lint` — без ошибок
- `docker-compose up --build` — сборка успешна
- `GET /api/health` → 200

### Пользователь (вручную в MAX)
1. Открыть чат с MAX-ботом → получить фото + кнопку "Открыть магазин"
2. Нажать кнопку → Mini App открылся, каталог загружен
3. Добавить товар в корзину → закрыть и открыть снова → корзина загружена с сервера
4. Оформить заказ с доставкой COURIER (адрес + дата/время) → получить подтверждение
5. Оформить заказ с самовывозом PICKUP → получить подтверждение
6. Менеджер получил уведомление в MAX с форматированием (жирные заголовки полей)
7. Администратор: отправить `/mode` → переключить режим → в приложении включился admin mode
8. Администратор: создать/заблокировать товар в admin mode

## Деплой

### Что нужно сделать перед деплоем

1. Обновить `api/.env`:
   - `BOT_TOKEN` → токен MAX-бота (с `dev.max.ru`)
   - `APP_URL` → URL Mini App
2. Обновить `manager_chat_id` в таблице `settings` — MAX user ID менеджера (через SQL на сервере)
3. Привязать Mini App к боту: `dev.max.ru → Чат-боты → [бот] → Мини-приложение → вставить URL`
4. `docker-compose up --build -d`

### Откат
- `git checkout <предыдущий коммит>` + `docker-compose up --build -d`
- Вернуть старый `BOT_TOKEN` в `.env`
- БД: таблица `user_cart` добавлена через `ALTER TABLE` / `CREATE TABLE IF NOT EXISTS` — откат не требует изменений схемы (данные старой корзины не используются)

## Риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| `requestContact()` в MAX работает иначе, чем в документации | Средняя | Stub-реализация, уточнить при тестировании |
| Сервер недоступен при работе с корзиной | Низкая | Показывать ошибку пользователю; локальный React state не теряется до перезагрузки |
| MAX Bot API имеет другой rate limit или структуру ошибок | Низкая | httpx возвращает исходный ответ, логировать для диагностики |
| HMAC алгоритм MAX имеет тонкие отличия от Telegram (encoding, сортировка) | Средняя | Тестировать с реальным initData MAX в первую очередь; при провале — сверить с `dev.max.ru/docs/webapps/validation` |
| Long polling падает при потере сети, дублирует события | Средняя | Обработка исключений + sleep(5) при ошибке; marker предотвращает дубли |
| manager_chat_id в MAX отличается от Telegram ID менеджера | Высокая | Обязательный ручной шаг перед деплоем |

## Критерии приёмки

**Сборка:**
- [ ] `npm run build` завершается без ошибок TypeScript и Vite
- [ ] `npm run lint` не выдаёт ошибок
- [ ] В коде нет обращений к `window.Telegram` (подтверждается grep)
- [ ] Файл `app/src/types/telegram.d.ts` удалён

**Бот и авторизация:**
- [ ] При открытии чата с ботом пользователь получает сообщение с фото, текстом и кнопкой
- [ ] Кнопка открывает Mini App (не выдаёт ошибку)
- [ ] Каталог товаров загружается (означает успешную авторизацию через MAX initData)
- [ ] Неверная подпись initData возвращает HTTP 401

**Корзина:**
- [ ] Товар добавлен в корзину → приложение закрыто и открыто → товар в корзине остался (загружен с сервера)
- [ ] Корзина доступна с разных устройств под одним аккаунтом
- [ ] После оформления заказа корзина пуста
- [ ] `GET /api/cart` возвращает текущую корзину пользователя
- [ ] `PUT /api/cart` обновляет состав корзины
- [ ] `DELETE /api/cart` очищает корзину

**Оформление заказа:**
- [ ] Заказ COURIER создаётся успешно (адрес + дата/время + опционально открытка)
- [ ] Заказ PICKUP создаётся успешно (выбор адреса самовывоза)
- [ ] При отсутствии телефона запрашивается контакт через WebApp.requestContact()
- [ ] После получения контакта телефон сохраняется, заказ продолжает оформляться
- [ ] Пользователь отклонил requestContact() → показывается объяснение, заказ не оформляется

**Уведомления:**
- [ ] Менеджер получает сообщение в MAX при создании заказа
- [ ] Сообщение содержит данные заказа с Markdown-форматированием (жирные метки полей)

**Admin функциональность:**
- [ ] Администратор может создать товар в admin mode (форма сохраняется без ошибок)
- [ ] Администратор может заблокировать товар (статус меняется, товар скрывается из каталога)
- [ ] Команда `/mode` переключает режим, изменение отражается в UI приложения

**Регрессия:**
- [ ] Заказы и данные пользователей из БД не потеряны
- [ ] `GET /api/health` возвращает 200
- [ ] При недоступном MAX WebApp SDK (тест в браузере без SDK) приложение не падает с uncaught exception
